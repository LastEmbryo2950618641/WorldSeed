# Worldseed：推演历史、世界线与版本恢复设计

## 1. 目标

本文定义 Worldseed 的长期推演历史能力，使用户可以保存、浏览、返回和分叉过去的世界状态，同时不破坏正在运行的任务检查点机制。整体交互接近 Photoshop 的历史记录面板：每个完整轮都是一个可重新选择的历史状态，选择旧状态不会删除新状态。

该能力必须满足：

- 用户可返回上一轮自动保存的世界状态，当前轮仍保留在历史列表中；
- 用户可查看手动保存与完整轮自动保存形成的历史列表；
- 推演历史列表默认无上限，用户可为项目配置保留数量上限；
- 设置上限后，每新增一个保存点都自动删除超额范围内最旧的历史保存点；
- 任一历史点都能恢复当时的上下文链、世界图、章节正文、用户 Markdown、规则快照、当前状态和任务检查点；
- 从历史点继续时创建新的世界线，原世界线及其后续历史仍然保留；
- 手动保存可以在任意时刻触发；
- 完整一轮成功后自动保存；
- 模型请求执行期间手动保存时，保存该请求开始前最近的稳定检查点，不中断当前请求；
- 恢复任何包含任务检查点的保存点后，任务统一处于暂停状态，不自动请求模型；
- 恢复和继续不能隐式重置时间、调用次数、Token、检索轮次或其他额度；
- 内部版本系统与 Worldseed 源码 Git、用户自己的 Git、系统 Git 配置和凭据完全隔离。

本文只定义长期历史和世界线。单轮内部如何中断、保存稳定检查点、续跑、重试和重置额度，见 [推演中断、确认与恢复设计](turn-interruption-recovery.md)。

## 2. 两类机制必须分离

### 2.1 任务检查点

任务检查点是某条世界线中一轮未完成推演的运行状态，解决：

- 当前执行到哪个阶段；
- 哪些 AI 请求已经完成；
- 哪些读取、输出和 pending 图修改已经产生；
- 出错或超限后从哪里继续；
- 用户如何暂停、继续或重试当前阶段。

任务检查点可以频繁生成，是执行恢复数据，不等于一个用户可见的世界版本。

### 2.2 推演历史

推演历史是用户可浏览、命名、恢复和分叉的长期保存点，解决：

- 当时完整世界是什么状态；
- 当时位于哪条世界线；
- 当时有哪些章节、Markdown、图修订和上下文；
- 当时是否存在未完成任务；
- 从该点继续后如何保留原来的未来。

### 2.3 包含关系

任务检查点属于某条世界线，并可被某个推演历史保存点引用。推演历史不复制或改写检查点语义，只冻结“这个保存点使用哪个稳定检查点”。

一个保存点可以处于以下两种状态：

- `complete_world`：完整一轮提交后的稳定世界，没有待续跑任务；
- `paused_checkpoint`：引用某个稳定任务检查点，恢复后任务保持暂停。

因此，任务检查点是历史保存内容的一部分，但二者不是同一需求，也不能使用同一个状态机代替。

## 3. 核心原则

### 3.1 历史不可变

已创建且仍在保留范围内的保存点、图修订、文档版本、章节版本、上下文片段和检查点不可原地覆盖。修改当前世界只能创建新版本并移动当前指针。用户配置的历史保留策略可以删除超额保存点，但不能原地改写仍保留的保存点。

### 3.2 恢复不删除未来

恢复过去保存点不会因为恢复动作本身删除该点之后的历史。用户从过去继续时，系统创建新世界线；原世界线保持可浏览、可恢复。只有用户启用的历史保留上限可以按统一淘汰规则删除最旧保存点。

### 3.3 恢复后不自动执行

只要保存点包含任务检查点，恢复后的任务状态固定为 `paused`。即使保存前任务正在执行，恢复时也不能自动重放模型请求。

### 3.4 保存进行中的请求不抢占执行器

模型请求不是稳定检查点。请求期间手动保存时：

1. 读取该任务最近的已持久化稳定检查点；
2. 创建引用该检查点的手动保存点；
3. 记录“保存发生时存在一个更新的在途操作”；
4. 不取消、不暂停、不等待当前模型请求；
5. 恢复该保存点时从被引用的稳定检查点呈现为暂停状态。

### 3.5 额度只由用户显式重置

保存、恢复、返回上一轮、切换世界线和从历史继续都不能重置额度。恢复的任务继承保存点中的额度窗口和累计用量；若指标已阻塞，用户必须在运行监控中显式重置后才能继续。

### 3.6 当前投影可以重建

SQLite 中的当前图、全文检索、章节头和任务头是某个历史保存点的活动投影，不是唯一历史真相。它们必须能由历史清单与不可变对象重新构建。

### 3.7 用户工作目录保持纯净

内部版本库、SQLite、对象、锁和索引不能写入用户 Markdown 工作目录。用户工作目录继续只呈现协议允许的文件夹和 `.md` 文件。

### 3.8 不使用 Git 术语污染产品交互

界面使用“推演历史”“世界线”“保存点”“从这里继续”“恢复到这里”，不向普通用户展示 commit、branch、checkout、detached HEAD 等 Git 术语。

## 4. 保存类型

### 4.1 手动保存

用户可在任何时刻点击“保存当前推演”。保存点至少记录：

- 保存名称和可选备注；
- 当前世界线；
- 当前完整世界头；
- 当前历史头；
- 当前用户工作目录快照；
- 当前章节集合与每章版本；
- 当前图修订头集合；
- 当前上下文链头；
- 当前规则、资料目录和检索索引版本；
- 当前额度窗口与累计用量；
- 最近稳定任务检查点；
- 保存时是否存在在途操作。

若没有未完成任务，手动保存为 `complete_world`。若存在未完成任务，则保存为 `paused_checkpoint`，引用最近稳定检查点。

手动保存不会改变正在运行任务的状态，也不会把 pending 内容提交为世界事实。

### 4.2 自动保存

一整轮推演完成以下最终化后自动保存：

1. 正文版本已提交；
2. 图修订和资料引用已提交；
3. 章节 Markdown 已发布；
4. 检索投影已更新或标记为可重建；
5. 世界头移动成功；
6. 不存在未决 finalization。

自动保存始终为 `complete_world`，同时更新：

- `worldHeadEntryId`：最新完整世界状态；
- `historyHeadEntryId`：当前世界线最新保存点。

自动保存失败不能回滚已经成功提交的世界，而应进入可恢复 finalization，由用户选择重试、暂停或稍后处理。

### 4.3 保存点命名

默认名称应便于识别，不依赖内部 ID：

- 自动保存：`第十二轮完成 · 第二章 雨夜来客`；
- 手动保存：`手动保存 · 2026-08-07 21:35`；
- 用户可编辑手动保存名称和备注，但编辑元数据不改变保存内容。

### 4.4 历史保留上限

每个项目提供 `historyRetentionLimit`：

- 默认值为 `null`，表示无上限；
- 用户可设置任意正整数；
- 统计对象为推演历史列表中的全部手动保存和自动保存；
- 任务内部稳定检查点、阶段重试记录和 finalization 记录不计入该上限；
- 手动保存与自动保存采用同一保留规则，不默认保护或置顶任何类型；
- 历史列表显示当前数量和上限，例如 `128 / 无上限` 或 `48 / 50`。

每个新保存点完成 finalization 后执行一次保留结算：

1. 读取项目当前全部可见历史保存点；
2. 按 `createdAt` 升序排列，相同时间按稳定 `historyEntryId` 排序；
3. 若数量超过上限，从最旧保存点开始删除，直到数量等于上限；
4. 被删除保存点立即从历史列表、比较、恢复和“从这里继续”入口消失；
5. 保存删除记录和原因 `retention_limit_exceeded`，用于诊断但不能恢复已删除世界；
6. 对不再被任何保留保存点、世界线、任务检查点或恢复操作引用的内部对象执行延迟垃圾回收。

当用户把“无上限”改为有限值，设置界面必须显示将删除的历史数量和最旧时间范围。用户确认后立即执行同一保留结算，而不是等到下一轮保存。增大上限或重新改为无上限不能恢复已经删除的保存点。

保留上限按整个项目统计，不按世界线分别计算。若待删除保存点是某条世界线的分叉基点或内部父节点，先把该世界线最早仍保留的保存点重建为独立基线；若某条非当前世界线的全部保存点都被淘汰，该空世界线也从历史列表删除。若用户正在查看即将删除的旧保存点，降低上限的确认面板必须说明活动游标将移动到哪个仍保留保存点，并在删除完成后原子切换，不能留下指向已删除历史的游标。

每个保存点都必须是可独立恢复的完整快照清单。删除一个旧保存点不能导致仍保留的后续保存点失去图、章节、Markdown、上下文或任务对象。若内部 Git 的父链仍引用待删除提交，保留结算必须先为最早保留点建立等价的新历史基线并原子移动内部引用，再把旧提交交给垃圾回收；不能仅从 SQLite 隐藏记录而永久保留一条无限增长的 Git 祖先链。

## 5. 世界线模型

### 5.1 世界线

世界线表示从某个历史点向后持续发展的推演分支。每个项目至少有一条初始世界线。

世界线保存：

- 自身 ID、名称和创建原因；
- 父世界线与分叉保存点；
- 当前完整世界头；
- 当前历史头；
- 当前工作检查点；
- 当前上下文链头；
- 创建时间、最后活动时间和归档状态。

### 5.2 三个不同的头

- `worldHeadEntryId`：当前世界线最新完成并正式提交的世界；
- `historyHeadEntryId`：当前世界线最新的手动或自动保存点；
- `workingCheckpointId`：当前未完成任务的最新稳定检查点，可为空。

另保存 `continuationContextHeadId`，明确下一次推演从哪条上下文链继续，避免仅恢复图而丢失模型已读历史。

这几个指针不能合并：手动保存可能更新历史头，却不能把 pending 内容提升为完整世界头。

### 5.3 从历史继续

用户选择“从这里继续”时：

1. 读取保存点完整性清单并校验对象；
2. 创建以该保存点为父节点的新世界线；
3. 物化该保存点的活动投影；
4. 恢复章节、Markdown、图头、上下文头和状态；
5. 若保存点包含任务检查点，将任务恢复为 `paused`；
6. 将新世界线设为当前世界线；
7. 等待用户显式编辑、继续任务或开始下一轮。

原世界线不移动、不覆盖、不删除。

### 5.4 切换与查看

用户可以只查看另一条世界线而不改变当前写入目标。只有明确执行“切换到此世界线”或“从这里继续”后，活动投影和后续写入目标才改变。

## 6. 返回上一轮

“返回上一轮”是历史面板的快捷导航：把活动历史状态切换到当前完整轮之前的自动保存点。它不是撤销命令，也不删除、反做或覆盖当前轮。

### 6.1 已完成的轮次

当前轮已经自动保存时，“返回上一轮”定位到紧邻当前轮之前的自动保存点：

- 当前轮的自动保存点继续保留在原世界线历史中；
- 章节、图、Markdown、上下文和当前状态切换为上一轮保存点的投影；
- 用户在产生新内容前仍可在历史面板回到当前轮或其他保存点；
- 仅查看或返回上一轮不会立即创建新世界线；
- 用户从该旧历史点开始新的推演或产生持久化修改时，系统才在首次写入前创建新世界线。

这种“先选择历史状态、后续写入时分叉”的行为接近 Photoshop 历史记录面板，但 Worldseed 不清除被跳过的未来历史。

### 6.2 未完成的轮次

“返回上一轮”只针对已经完成并自动保存的轮次。当前轮仍在 pending、执行中或暂停状态时，用户应先通过任务控制选择暂停或停止；系统不能把未完成任务伪装成一个已经完成的轮次。

若用户停止当前未完成任务并返回最近完整轮，任务和检查点不物理删除，而是保留在任务历史中；它们不进入完整轮时间线，也不成为新的世界事实。

### 6.3 历史游标与延迟分叉

历史面板维护一个“当前选中保存点”，它可以暂时位于世界线 head 之前。只读查看和历史切换只移动该游标；任何章节编辑、规则修改、图修改或新一轮推演在写入前都必须检测游标是否位于 head：

- 位于 head：继续当前世界线；
- 不位于 head：先从选中保存点创建新世界线，再执行写入；
- 原世界线、当前轮及更晚保存点全部保留。

系统不能直接用旧投影覆盖后继续写入同一世界线，也不能复用已被后续世界修改污染的 SQLite 当前投影。

## 7. 必须恢复的完整状态

恢复不是只恢复章节文件，也不是只切换图 head。一个保存点的完整性清单必须覆盖以下内容。

### 7.1 世界图

- 节点与连接的有效修订头；
- AI 定义的出口内容、出口查询规则和归档出口；
- 当前状态与历史返回路径；
- 修订依据、决定记录和 SourceRef；
- 当前世界线可见的检索投影版本。

图对象继续使用不可变修订。保存点只冻结该世界线当时采用哪些修订，不复制一套可变图。

### 7.2 章节与原文

- 章节顺序；
- 每章标题、文件路径和正文版本；
- 正文单元、结算记录和来源引用；
- 已发布与待发布状态；
- 用户对章节的后续编辑版本。

恢复后工作目录中的 `章节正文` 必须与保存点的章节头一致。

### 7.3 用户 Markdown

- `世界推演规则/用户规则`；
- `设定集`；
- `参考文件`；
- `表现输出`；
- `章节正文`；
- 固定目录和不可删除 `readme.md` 的当时内容。

基础规则属于应用版本锁定资源，保存点记录其版本和摘要，不允许历史恢复把应用安装资源改写到用户目录。若当前应用缺少该历史点要求的基础规则版本，恢复必须暂停并提示兼容性问题。

### 7.4 上下文链

- `TurnContext` 及其父链；
- 原始 ContextSegment；
- 压缩检查点和被覆盖片段关系；
- 实际读取证据与 unresolved dependencies；
- RuleSnapshot；
- 模型配置引用，不包含明文 API Key；
- KV 使用指标和可复用前缀身份；
- 下一次继续使用的上下文头。

KV 缓存本身不要求跨恢复长期保存；恢复的是可确定重建稳定前缀的上下文身份。缓存未命中只影响成本和时间，不能改变世界事实。

### 7.5 任务与额度

- 任务状态、阶段运行和执行游标；
- pending scope；
- 稳定检查点；
- 中断原因、重试代次和租约状态；
- 当前额度窗口；
- 累计 Token、调用和耗时；
- finalization 状态。

恢复时旧租约一律失效；包含任务的保存点恢复为 `paused`，由用户重新取得执行权。

## 8. 内部 Git 方案

### 8.1 技术选择

使用开源 `isomorphic-git` 作为应用内版本对象实现，不调用系统 Git CLI，也不魔改 Git 协议。

选择理由：

- Node.js/Electron 可直接调用；
- 可显式指定文件系统和仓库目录；
- 不依赖用户安装 Git；
- 不读取系统 Git 配置即可完成本地对象、树、提交和引用管理；
- 便于封装为基础设施适配器，与业务世界线模型隔离。

### 8.2 物理隔离

每个项目使用独立内部裸仓库：

```text
AppData/Worldseed/projects/<projectId>/
├─ project.sqlite
├─ history.git/
├─ objects/
├─ emergency-recovery/
└─ logs/
```

强制约束：

- 用户工作目录中不创建 `.git`；
- 不设置进程级 `GIT_DIR` 或 `GIT_WORK_TREE`；
- 不读取或写入全局、系统、用户级 Git config；
- 不使用系统 credential helper；
- 不执行仓库 hooks；
- 不配置 remote，不自动 fetch 或 push；
- 不继承用户 Git 身份；
- 内部提交使用固定应用身份和本地时间；
- 所有仓库路径由 `projectId` 经过规范化后在应用数据根目录内解析。

Worldseed 源码仓库和用户自己的仓库因此不会被内部历史操作发现或修改。

### 8.3 Git 存储内容

每个保存点对应一个内部不可变提交。树中保存版本清单和内容寻址对象引用，而非提交正在运行的 SQLite 文件。

建议树结构：

```text
manifest.json
workspace/
  <用户可见 Markdown 快照>
world/
  graph-heads.json
  chapter-heads.json
  document-heads.json
  source-heads.json
context/
  continuation-head.json
  checkpoint-ref.json
runtime/
  budget-snapshot.json
  task-snapshot.json
objects/
  <仅放适合 Git 去重的小型不可变对象或对象清单>
```

大型不可变载荷可以保存在应用内部对象库，Git 树只保存内容摘要、对象 ID、大小和完整性校验。对象垃圾回收必须从所有保存点、世界线、检查点和紧急恢复信封计算可达性，不能只看当前世界线。

历史保留上限要求 Git 适配器支持“重建保留边界”：最早仍保留保存点可以被复制为内容完全相同、无已删除父链的新基线提交，后续保留历史再接到该基线上。该操作只改变内部版本拓扑和提交 ID，不改变任何保留保存点的 manifest 摘要、用户可见内容、保存时间或世界语义。

### 8.4 Git 不承担的职责

内部 Git 不直接承担：

- 当前任务队列和执行租约；
- SQLite 查询事务；
- FTS 或向量索引；
- 当前世界图邻接投影；
- 模型调用流式片段；
- API Key 和凭据；
- UI 状态。

这些仍由 SQLite、对象库和 Electron 安全存储负责。Git 负责不可变历史、父子关系、世界线引用和内容快照完整性。

## 9. SQLite 与 Git 的职责

### 9.1 SQLite

SQLite 保存可查询的活动状态和历史元数据：

- 项目与当前世界线；
- 世界线和历史条目索引；
- 当前图、文档、章节、上下文投影；
- 任务、检查点、阶段运行、中断和租约；
- 检索索引构建状态；
- 保存、恢复和 checkout finalization；
- Git 提交 ID 与完整性摘要的映射。

### 9.2 Git

Git 保存：

- 保存点不可变树；
- 保存点父链；
- 世界线引用；
- 用户 Markdown 内容快照；
- 各类不可变对象头清单；
- 保存点完整性摘要。

### 9.3 一致性协议

保存采用可恢复 finalization：

1. 冻结 SQLite 中的保存清单；
2. 写入缺失对象并校验摘要；
3. 创建 Git tree 和 commit；
4. 在 SQLite 登记历史条目；
5. 更新内部世界线 ref；
6. 更新 SQLite 的历史头；
7. 标记保存完成。

任一步失败都保留 finalization 记录，不能删除已写对象。重试必须幂等，使用相同 `historyEntryId` 和内容摘要收敛到同一保存点。

恢复采用准备、物化、切换三阶段：

1. 校验保存点和全部必需对象；
2. 在新 generation 中重建 SQLite 投影和临时工作目录；
3. 原子切换当前世界线、活动 generation 和用户工作目录发布头。

恢复失败时继续使用恢复前世界线，不允许留下图已切换但章节未切换的混合状态。

## 10. 建议契约

### 10.1 核心记录

- `WorldBranch`：世界线身份、父线、分叉点和各 head；
- `HistoryEntry`：保存点身份、类型、父保存点、Git 提交和完整性状态；
- `HistoryManifest`：恢复所需对象的完整清单；
- `WorkspaceSnapshot`：用户 Markdown 路径、内容摘要和权限属性；
- `WorldProjectionHeads`：图、章节、文档、来源与上下文头；
- `SavedTaskState`：稳定检查点、pending scope、额度和暂停恢复语义；
- `HistoryFinalization`：保存或恢复各步骤的幂等状态；
- `ActiveProjectionGeneration`：当前 SQLite 与工作目录投影代次；
- `HistoryRetentionPolicy`：项目历史上限、最近结算时间和待回收边界。

### 10.2 端口边界

- `HistoryRepository`：历史条目、世界线和 head 元数据；
- `VersionObjectStore`：内容寻址对象读写和完整性验证；
- `HistoryVcsPort`：创建提交、读取树和移动内部世界线引用；
- `HistoryManifestBuilder`：从稳定数据库视图构建完整清单；
- `ProjectionMaterializer`：从清单重建活动投影；
- `WorkspaceSnapshotPort`：快照并发布用户 Markdown；
- `HistoryFinalizationRepository`：保存和恢复的可重入步骤；
- `HistoryFacade`：向 Electron 暴露用户语义接口。

业务层不能直接调用 `isomorphic-git`。`isomorphic-git` 只能存在于 `infrastructure/history-git` 适配器中。

### 10.3 建议接口

- `history.list(projectId, branchId?)`；
- `history.get(entryId)`；
- `history.saveManual(projectId, name?, note?)`；
- `history.restore(entryId)`；
- `history.continueFrom(entryId, branchName?)`；
- `history.returnToPreviousRound(projectId)`；
- `history.listBranches(projectId)`；
- `history.switchBranch(branchId)`；
- `history.renameBranch(branchId, name)`；
- `history.renameEntry(entryId, name, note?)`；
- `history.retention.get(projectId)`；
- `history.retention.preview(projectId, limit)`；
- `history.retention.update(projectId, limit)`；
- `history.finalization.status(operationId)`；
- `history.finalization.resume(operationId)`。

所有改变当前世界线或工作目录的接口都使用项目级单写者，并要求幂等操作 ID。

## 11. UI 设计

### 11.1 入口

顶部“推演”菜单增加：

- 保存当前推演；
- 返回上一轮；
- 打开推演历史。

右侧工具窗口增加“推演历史”Tab，也可从顶部菜单打开。

### 11.2 历史列表

列表按世界线分组，默认显示当前世界线，条目展示：

- 保存名称；
- 手动保存或自动保存；
- 所属章节和轮次；
- 保存时间；
- 完整世界或暂停检查点；
- 是否包含未完成任务；
- 保存时是否存在在途请求；
- 与当前点的章节、图修改和 Markdown 变化摘要。

历史列表使用紧凑时间线，不使用大卡片。用户可筛选“全部、自动保存、手动保存、含暂停任务”。

历史面板顶部同时显示 `当前数量 / 保留上限`。默认显示“无上限”。达到有限上限后，新保存点写入完成，最旧保存点自动从列表消失；状态栏显示本次删除数量和内部清理进度。

### 11.3 条目操作

- `查看`：只读预览，不改变当前世界；
- `恢复到这里`：恢复内容并切换活动状态，包含任务时保持暂停；
- `从这里继续`：创建新世界线并切换；
- `重命名`：只改显示元数据；
- `比较`：比较章节、Markdown、图修订头和任务状态；
- `归档世界线`：隐藏非当前世界线，不删除历史。

“恢复到这里”和“从这里继续”必须清楚说明原未来不会删除。若操作会替换当前未保存状态，先引导创建手动保存。

项目设置增加“推演历史”分类，提供“保留数量”选项：

- 默认选择“无上限”；
- 切换为“限制数量”后使用正整数输入框；
- 降低上限时即时预览将删除多少个最旧保存点及其时间范围；
- 用户确认后立即执行，界面明确提示删除不可恢复；
- 增大上限只影响后续保留，不恢复此前删除内容。

### 11.4 手动保存反馈

普通状态下保存后立即在底部状态栏显示保存名称和完成状态。

模型请求期间保存时显示：

> 已保存最近稳定检查点。当前模型请求仍在继续；恢复此保存点时任务将处于暂停状态。

不能显示成“已保存当前生成内容”，因为在途流式内容尚未成为稳定检查点。

### 11.5 恢复确认

确认面板必须展示：

- 目标世界线和保存点；
- 将恢复的章节、图、Markdown 和上下文范围；
- 是否包含暂停任务及恢复阶段；
- 当前未保存变化如何处理；
- 当前额度窗口和阻塞指标；
- 原世界线未来将继续保留；
- 恢复后不会自动运行模型。

恢复完成后，中央区域打开该保存点的最后活动文档；右侧流程栏显示“已从历史恢复，任务已暂停”，并提供用户可控的继续入口。

## 12. 与现有线性实现的差距

当前代码中的 `projects.committed_sequence`、全局 `committed` 作用域和单一当前章节头只支持线性世界。现有基础可以复用：

- `artifact_scopes` 的 pending、committed、retired 隔离；
- 不可变图修订；
- 不可变文档版本；
- `turn_contexts` 与 `phase_runs`；
- `rule_snapshots` 和 Evidence；
- 作用域原子提交。

正式实现前仍需补齐：

- 保存点 DAG 与世界线模型；
- 分世界线的图修订头；
- 分世界线的检索活动投影；
- 分世界线的章节和文档头；
- 完整用户 Markdown 内容快照；
- 分世界线的上下文父链和 continuation head；
- 历史保存、恢复和 checkout finalization；
- 用户可见历史 UI。

不能只在现有 `committed_sequence` 上增加一个“历史序号”，否则恢复后继续仍会覆盖线性未来，检索也会混入其他世界线事实。

## 13. 测试与验收

### 13.1 必测场景

1. 完整一轮结束后自动保存，恢复后章节、图、上下文和 Markdown 摘要一致；
2. 空闲时手动保存，修改多个 Markdown 后恢复，文件内容与目录完全回到保存点；
3. 模型请求期间手动保存，不中断请求，保存点引用请求前稳定检查点；
4. 恢复上述手动保存点后任务为 `paused`，不会自动调用模型；
5. 从旧自动保存继续，创建新世界线，原世界线后续仍可查看；
6. 返回上一轮后当前轮自动保存仍存在，且在产生新写入前可以重新选回；
7. 从上一轮开始新推演时才创建新世界线，原世界线未来保持可见；
8. 恢复已超限检查点，继续按钮保持阻塞，用户显式重置后才可继续；
9. 保存过程中进程退出，重启后 finalization 能幂等完成；
10. 恢复过程中进程退出，重启后保持旧活动世界或继续完成切换，不出现混合状态；
11. 一条世界线重建 FTS 后，不能召回另一条世界线独有事实；
12. 同一图对象在两条世界线产生不同后续修订，各自查询得到各自当前状态；
13. 恢复旧章节集合后，用户工作目录不存在后来章节，但原世界线仍保有后来章节；
14. 用户工作目录本身处于 Git 仓库时，内部保存不会改变其 `.git`、索引、分支或工作树；
15. Worldseed 源码仓库和系统 Git config 在内部保存前后字节与状态不变；
16. 内部仓库对象损坏时，恢复在切换前停止并报告可修复问题；
17. 两次相同操作 ID 的保存只产生一个逻辑历史条目；
18. 大型长期项目恢复后，图索引可后台重建且正文与历史浏览仍可用；
19. 默认无上限时连续保存不会自动删除任何历史点；
20. 上限为 `10` 时创建第 `11` 个保存点，最旧保存点被删除且其余十个均可完整恢复；
21. 连续跨越多条世界线保存时仍按项目创建时间稳定淘汰最旧保存点；
22. 将现有一百个保存点的上限改为二十，确认后立即删除最旧八十个；
23. 删除旧 Git 祖先后，最早保留点仍可独立恢复，内部对象存储不存在永久增长的已删除祖先链；
24. 任务检查点数量增长不影响历史列表保留计数；
25. 增大上限或恢复无上限不会重新出现已删除保存点。

### 13.2 验收标准

- 任一保存点都能确定其世界线、父保存点、完整清单和内容摘要；
- 手动保存与自动保存语义明确且在 UI 可区分；
- 在途请求期间保存只冻结最近稳定检查点；
- 恢复包含检查点的保存点后任务必为暂停；
- 恢复、返回上一轮和分叉不自动重置任何额度；
- 从历史继续不会删除或覆盖原未来；
- 默认历史保留数量无上限，有限上限只在用户明确配置后生效；
- 超过有限上限时严格按创建时间删除最旧保存点，数量最终等于上限；
- 删除任一旧保存点不会破坏仍保留保存点的独立恢复能力；
- 图、章节、Markdown、上下文和状态不会跨世界线串读；
- 用户工作目录不出现内部 `.git` 或内部数据库；
- 内部 Git 不接触系统 Git 配置、凭据、hooks 和 remotes；
- 保存与恢复均可在进程中断后幂等收敛；
- 当前投影可以从保存点完整重建；
- UI 全程使用世界线和推演历史语义，不要求用户理解 Git。

## 15. 最终定义

Worldseed 的推演历史不是对当前文件夹做简单备份，也不是把任务检查点改名为存档，而是：

> 以不可变保存点冻结完整世界，以世界线保留不同未来，以任务检查点恢复未完成执行，并由隔离的应用内 Git 保存长期版本关系。

Git 只提供版本对象和分支能力；SQLite 负责活动投影、任务与检索；AI 仍负责世界图语义和演化。任何恢复都必须同时恢复图、正文、用户资料、上下文和当前状态，且包含任务时统一暂停，由用户决定下一步。
